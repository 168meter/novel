## 原因、资源与剩余边界

修复前页面先查带双 ID 条件的书章元数据，正文 Service 又按章节 ID 查询一次归属。优化复用服务端私有构造、不可篡改的 `OwnedChapter` 结果；原双 ID Service 直接调用仍独立校验。保留原 VIP、导航、正文 SQL、缓存 Key、连接池与执行器配置。

- **物理SQL：每请求4→3，减少25%**。修复前每轮60次重复 `metadata-id` SELECT 被消除；带 bookId/chapterId 条件的归属查询仍有60次，书籍查询60次、导航查询60次。三版均为正文热缓存，`book_content0..9` SELECT 都为0；不能把这次收益误写成正文SQL再次减少25%。
- 数据库服务器语句累计时间折算每请求：baseline 0.5552ms、修复前0.7634ms、优化后0.6205ms。它不含网络往返、ShardingSphere/MyBatis、线程调度或模板渲染，不能单独解释客户端P95变化。
- 原始 Prometheus 实际含阅读 HTTP timer。自动摘要的 `httpCount/httpSeconds=null` 是解析正则未兼容 URI 标签中的 `{bookId}` / `{bookIndexId}`；**不是应用未暴露指标**。本次从保存的原文离线恢复，各窗口 HTTP count 增量均60，与客户端一致；三轮服务端整请求平均耗时为13.1996 / 16.0498 / 14.3178ms（baseline / 修复前 / 优化后）。没有模板等内部阶段的单独计时，不能把余下耗时认定为模板瓶颈。未为此改脚本或重跑实验，原始摘要保留。
- 各版本每轮进程CPU时间增量均值分别为2.86 / 3.40 / 2.98秒。包含窗口内JIT和后台活动，不等于CPU利用率或稳态容量。GC测量窗口内分别为2次共12ms / 0次 / 1次共5ms；优化版第三轮有5ms GC，但缺少逐请求关联证据，不能断言它导致全部尾延迟反向。
- 优化版 Heap 窗口前为163.30—234.90MiB，窗口后168.59—261.45MiB；GC会改变前后差值，不能据此推断长期内存占用或泄漏。9轮窗口后业务执行器 active/queue、Hikari active/pending均0，Hikari timeout计数前后均0；这些快照不能证明窗口内峰值为0。
- 各版运行配置指纹一致，前台内存限制896MiB，CPU未设置配额（NanoCpus=0）。因此结果不构成固定2C4G容量证明。每轮实际测量仅约0.6—0.85秒；60样本下最近秩P99就是该轮最大值。RPS包含PowerShell客户端调度成本，均不应包装为持续高并发性能成果。

历史 `deploy-20261017233540699` 的 baseline P95 24.4421ms、修复前37.0929ms（+51.76%）仍保留。本次**同一修复前镜像**重新测得26.1882ms，说明旧退化并未在相同幅度复现，存在明显时间/运行状态波动。不能直接用37.0929→24.4931计算并宣称优化收益。`reading-fix-20261018135654925` 在校准时因工具误报停止，没有正式轮次，不纳入性能表。

## 正确性与部署状态

优化版真实 HTTP 复核：使用另一真实书籍 ID 搭配当前章节，页面返回404；摘要 HTTP 200但业务码400、`ok=false`，按业务失败处理；正文缓存 lookup 计数保持0→0。此前25项相关 Java 回归覆盖 Service 直接调用、缓存无交互、凭证不可篡改及 VIP 购买行为，本轮未重复运行。

对账显示原五个实验容器、私有 admin 和验证 Redis 的 ID/镜像/启动时间未变，原库与验证库的书籍访问/评论计数快照一致。宿主机入口完成记录表明，优化前台镜像 `sha256:f40272a04637a0cded62c1ca6df3abcb29dea16dfc934cbeda99aabb862633c7` 已部署；这是本次运行结束时的状态，本次未向 Docker 查询实时状态。

**工程结论：保留此最小优化，结束本轮性能修复。** 可确定地描述为“保持书章归属校验及缓存隔离，消除重复数据库访问，小范围真实MySQL回归中每请求物理SELECT由4次降至3次，三轮540次请求无业务失败”。其中540次包含三个版本各180次；优化版自身是180/180次成功。不把不稳定的尾延迟百分比或短窗口RPS作为生产容量承诺。
