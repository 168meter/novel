# Novel-Plus 匿名阅读时长采集设计

## 1. 背景与目标

Novel-Plus 已完成章节缓存、防击穿、异步执行器容量治理、Kafka 访问量聚合和本地可观测性建设。现有书籍点击量只能说明详情页被访问，无法回答读者是否真正停留阅读，也不足以支撑后续按真实阅读热度改进推荐。

本阶段增加匿名阅读时长采集链路：浏览器只在章节页面持续可见且获得焦点时，每满 30 秒发送一次心跳；服务端使用 Redis 完成页面凭证校验、去重、限流和每日计时上限，再将被接受的 30 秒事件异步写入 Kafka。后续阶段再由 Kafka 消费者批量聚合到 MySQL，并接入推荐排序。

目标如下：

- 同时覆盖桌面端和移动端章节阅读页。
- 尽量排除后台标签页、最小化窗口和失焦窗口产生的无效时长。
- 使用服务端签发的页面访问凭证，避免客户端随意给任意章节增加时长。
- 使用 Redis 原子去重、限流和封顶，控制刷新、重放和并发请求。
- Redis 或 Kafka 故障时不影响章节正常阅读。
- 不采集登录身份，不把 Cookie、IP 或匿名会话标识写入 Kafka 和 MySQL。
- 为下一阶段的每日聚合及推荐特征提供版本化事件。

## 2. 本阶段边界

### 2.1 包含内容

- 复用并加固现有匿名浏览器 Cookie `userMark`。
- 章节成功渲染时生成并注册 `pageVisitId`。
- 桌面、移动章节模板接入同一份阅读心跳脚本。
- 新增同源阅读心跳接口。
- Redis Lua 原子完成页面绑定校验、序号去重、滑动窗口限流、每日上限和时长累加。
- 新增 Kafka 阅读时长事件及异步生产端。
- 新增 Micrometer 指标、自动化测试和学习文档。

### 2.2 不包含内容

- 本阶段不增加登录、邮箱验证码或真实用户身份绑定。
- 不实现 Kafka 消费者和 MySQL 阅读时长汇总表；它们属于下一阶段。
- 不在本阶段修改推荐算法；推荐只在汇总数据稳定后接入。
- 不统计鼠标、键盘、滚动轨迹，也不承诺识别屏幕前是否是真人。
- 不尝试跨浏览器、跨设备识别同一个人。
- 不使用 Redis 暂存时长后再迁移 MySQL，也不在请求线程直接写 MySQL。

## 3. 身份和时间语义

### 3.1 匿名浏览器身份

系统复用 `NovelFilter` 已创建的匿名标识；代码常量为 `USER_CLIENT_MARK_KEY`，实际 Cookie 名称为 `userClientMarkKey`，下文简称 `userMark`，不再增加第二个匿名 Cookie。`userMark` 是随机值，只代表当前浏览器配置文件，不能证明它对应某个真实自然人。

Cookie 调整为：

- 有效期 7 天。
- `HttpOnly`，前端 JavaScript 无法读取。
- `SameSite=Lax`。
- HTTPS 环境增加 `Secure`。
- Cookie 被清除、换浏览器或换设备后会获得新的匿名身份，这是本方案接受的边界。

服务端只使用 SHA-256 摘要参与 Redis 校验和计数，不在新链路中保存或发送原始 `userMark`。7 天只表示匿名浏览器身份的寿命，不表示阅读时长按 7 天合并。

### 3.2 服务端日期

每日统计边界统一使用服务端 `Asia/Shanghai` 日期。客户端不传日期，Redis 每日计时键和 Kafka 的 `statDate` 都由服务端生成。因此同一匿名浏览器连续两天阅读同一章节，会进入两个不同的每日计数周期。

### 3.3 页面访问身份

每次章节页面成功渲染后，服务端生成随机 `pageVisitId`。刷新页面会产生新的 `pageVisitId`。它只证明服务端近期确实渲染过该章节，不是用户身份，也不进入最终统计。

服务端在 Redis 保存两小时页面绑定：

```text
reading:page:{pageVisitId}
  sessionHash = 当前 userMark 的 SHA-256
  bookId      = 当前书籍 ID
  chapterId   = 当前章节 ID
  lastSequence = 已接受的最大序号
TTL = 2 小时
```

只有 Redis 注册成功，`pageVisitId` 才嵌入页面并启用心跳。Redis 不可用时章节仍正常显示，但这次页面访问不采集时长；Redis 恢复后刷新页面即可重新注册。

## 4. 浏览器心跳行为

桌面模板和移动模板引用同一份静态脚本，避免两套逻辑逐渐不一致。页面提供 `bookId`、`chapterId` 和服务端签发的 `pageVisitId`，脚本不读取 `HttpOnly` Cookie。

有效阅读时间定义为同时满足：

- `document.visibilityState === "visible"`；
- `document.hasFocus()` 为真。

行为规则如下：

1. 章节页面打开后不立即计时。
2. 连续处于有效阅读状态满 30 秒后，发送第一次心跳。
3. 每次被接受的心跳固定代表 30 秒，客户端不能自报秒数。
4. 标签页隐藏、浏览器最小化或窗口失焦时暂停并清空当前不足 30 秒的计时。
5. 恢复焦点后重新等待完整 30 秒，不补发离开期间的时长。
6. 每个页面访问维护从 1 开始递增的 `sequence`；刷新后新 `pageVisitId` 的序号重新从 1 开始。
7. 网络失败不补发旧序号，下一周期继续发送新序号，避免重试风暴。

这是一种低成本近似：它能排除明显的后台挂机，但不能证明用户一直注视或阅读页面内容。

## 5. HTTP 接口

新增同源接口：

```http
POST /engagement/reading/heartbeat
Content-Type: application/json

{
  "bookId": 2055879962859147264,
  "chapterId": 2055880123456789012,
  "pageVisitId": "服务端签发的随机值",
  "sequence": 1
}
```

参数约束：

- `bookId`、`chapterId` 必须为正整数。
- `pageVisitId` 必须满足服务端生成格式和长度限制。
- `sequence` 必须为正整数，并设置合理上限以拒绝畸形输入。
- 服务端从 `HttpOnly` Cookie 取得 `userMark`，客户端不能在请求体中指定匿名身份、日期或计时秒数。

处理顺序如下：

```text
校验请求格式
  -> 摘要 userMark，并计算服务端日期与 IP HMAC
  -> Redis Lua 原子判定
  -> ACCEPTED 时异步发送 Kafka
  -> 快速返回
```

明显非法或缺少必要字段返回 HTTP 400。合法格式下，无论事件被接受、去重、限流、封顶，还是 Redis/Kafka 暂时失败，均返回统一成功响应，不向客户端暴露内部 Redis 键、限流阈值或依赖异常。具体结果只进入服务端指标和受控日志。

## 6. Redis 原子判定

### 6.1 Redis 数据结构

除页面绑定 Hash 外，使用以下键：

```text
reading:rate:session:{sessionHash}                 ZSET，TTL 约 2 分钟
reading:rate:ip:{ipHmac}                           ZSET，TTL 约 2 分钟
reading:credit:{yyyy-MM-dd}:{sessionHash}:{bookId}:{chapterId}  STRING，TTL 约 2 天
```

ZSET member 使用本次 `pageVisitId + sequence`，score 使用服务端毫秒时间。每日计时键保存当日已经接受的秒数。`pageVisitId` 不进入每日键，因此刷新页面不能重置每日上限。

### 6.2 滑动窗口而非自然分钟

会话限制为最近 60 秒最多接受 2 次，IP 限制为最近 60 秒最多接受 120 次。Lua 在每次判断时先删除 `now - 60s` 之前的 ZSET member，再检查剩余数量。

不能使用按 `yyyyMMddHHmm` 分桶的自然分钟计数器，否则攻击者可以分别在某分钟末尾和下一分钟开头发送请求，在两秒内消耗两个窗口额度。滑动窗口符合“任意最近 60 秒”的限制语义。

IP 只用于辅助抑制批量攻击。服务端使用由环境变量提供的密钥计算 HMAC-SHA256，Redis 和日志不保存原始 IP。公网环境必须配置非默认密钥，并由受控反向代理覆盖转发头；应用只信任该代理传入的客户端地址，不能直接信任任意来源的 `X-Forwarded-For`。

### 6.3 Lua 判定顺序

单个 Lua 脚本原子执行：

1. 页面键存在，并且其中的 `sessionHash`、`bookId`、`chapterId` 与本次请求完全匹配。
2. `sequence` 大于页面键保存的 `lastSequence`；否则判为重复或乱序。
3. 清理并检查会话最近 60 秒窗口，小于 2 次才继续。
4. 清理并检查 IP 最近 60 秒窗口，小于 120 次才继续。
5. 检查同一服务端日期、匿名会话和章节的已计时秒数；达到 1800 秒后不再增加。
6. 接受时更新 `lastSequence`、两个滑动窗口和每日秒数，一次增加固定 30 秒。

脚本返回内部结果：

- `ACCEPTED`
- `DUPLICATE`
- `INVALID_PAGE`
- `SESSION_RATE_LIMITED`
- `IP_RATE_LIMITED`
- `DAILY_CAP_REACHED`
- `REDIS_ERROR`（由 Java 层把调用异常归类）

Lua 使“检查条件”和“写入计数”不可被并发请求插入，从而不会因为多个同时到达的心跳突破每日上限或限流阈值。第一版按当前单实例 Redis 设计；如果未来迁移 Redis Cluster，需要重新设计 key hash-tag 或拆分状态，避免跨 slot Lua 限制。

## 7. Kafka 事件

只有 Redis 返回 `ACCEPTED` 才异步发送 Kafka。Topic 使用版本化名称 `novel-reading-engagement-v1`，消息 key 使用 `bookId`，便于后续同一本书的聚合事件保持分区稳定。

事件字段如下：

```text
eventId          全局唯一事件 ID
bookId           书籍 ID
chapterId        章节 ID
creditedSeconds  固定为 30
occurredAt       服务端接收时间
statDate         服务端 Asia/Shanghai 日期
version          1
```

事件明确不包含：原始 `userMark`、`sessionHash`、`pageVisitId`、IP、IP HMAC、邮箱或用户 ID。下一阶段 MySQL 只按书籍、章节和日期保存聚合结果，不保存匿名读者轨迹。

Redis 判定在 Kafka 发送之前完成。Kafka 异步发送失败时记录失败指标和限频日志，不回滚 Redis 已接受的 30 秒，也不降级为请求线程直写 MySQL。这可能少记一次 30 秒，但避免重复计时、同步阻塞和故障扩散；阅读热度属于允许近似的统计数据。

## 8. 故障与降级

| 场景 | 行为 | 用户阅读 |
|---|---|---|
| 渲染时 Redis 不可用 | 不签发可用 `pageVisitId`，不启动心跳 | 正常 |
| 心跳时 Redis 不可用 | 归类 `REDIS_ERROR`，不发 Kafka | 正常 |
| Kafka 异步发送失败 | 保留 Redis 已接受状态，记录失败 | 正常 |
| 心跳接口网络失败 | 浏览器不补发旧周期 | 正常 |
| 重复或乱序请求 | Redis 拒绝重复计时 | 正常 |
| 达到会话/IP限制 | 快速成功但不计时 | 正常 |
| 达到每日 1800 秒 | 快速成功但不计时 | 正常 |

所有依赖异常都不得向章节页面主流程抛出，不能因为统计功能降低核心阅读可用性。

## 9. 可观测性

新增指标至少覆盖：

- 心跳请求总数，按 `accepted`、`duplicate`、`invalid_page`、`session_rate_limited`、`ip_rate_limited`、`daily_cap_reached`、`redis_error` 分类。
- 被接受的阅读秒数。
- Redis Lua 调用耗时与异常数。
- Kafka 阅读事件发送成功、失败数。
- 页面凭证注册成功、失败数。

指标标签只能使用有限枚举，不能把 `bookId`、`chapterId`、`pageVisitId`、会话摘要或 IP 摘要作为标签，避免 Prometheus 高基数。日志同样不得输出 Cookie、原始 IP 和摘要；异常日志需限频，避免依赖故障造成日志风暴。

Grafana 后续增加阅读心跳接收速率、接受率、计入秒数、限流/封顶次数、Redis 错误和 Kafka 发送失败面板。告警重点关注 Redis 错误持续出现和 Kafka 发送失败，不对正常的重复、限流或每日封顶直接告警。

## 10. 测试设计

### 10.1 前端行为

- 桌面与移动章节模板均引入同一脚本并获得页面参数。
- 页面持续可见且聚焦不足 30 秒时不发送。
- 满 30 秒后发送一次，继续有效阅读时每 30 秒发送一次。
- 隐藏、最小化或失焦立即暂停；恢复后重新等待完整 30 秒。
- `sequence` 在同一页面递增，刷新后使用新的 `pageVisitId`。
- 网络失败不会立即循环重试或补发历史周期。

### 10.2 服务端单元与集成测试

- Cookie 的 7 天、`HttpOnly`、`SameSite` 和 HTTPS `Secure` 行为。
- 只有章节成功渲染才注册页面凭证；注册失败不影响渲染。
- 参数非法返回 400，合法但未计入的业务结果不暴露内部原因。
- 页面凭证必须与会话、书籍、章节完全匹配。
- 重复和乱序 `sequence` 只计入一次。
- 刷新后的新页面凭证不能绕过同章节每日 1800 秒上限。
- 会话最近 60 秒最多接受 2 次，覆盖自然分钟边界测试。
- IP 最近 60 秒最多接受 120 次。
- 并发请求不能突破限流和每日上限。
- Redis 异常时不发送 Kafka，接口和章节阅读不受影响。
- Kafka 异步失败只记录指标，不向阅读请求传播。
- Kafka 事件字段、固定 30 秒、服务端日期和隐私字段约束正确。
- 指标标签不存在高基数维度。

### 10.3 回归与运行验证

- 原有章节缓存、相邻章节预取、访问量 Kafka 聚合和执行器监控测试保持通过。
- 本地实际打开桌面、移动阅读页，观察失焦前后请求变化。
- 并发脚本重放相同及不同序号，验证 Redis 结果、Kafka 消息数和每日上限。
- 停止 Redis、Kafka 分别演练，确认章节仍可读取且监控出现相应失败指标。

## 11. 分阶段交付

本方案按以下顺序交付，避免一次同时引入采集、消费、存储和推荐，导致问题难以定位：

1. **当前阶段：采集与事件生产。** 浏览器心跳、Cookie 加固、页面凭证、Redis 原子闸门、Kafka 生产端、指标和测试。
2. **下一阶段：聚合落库。** Kafka 消费者批量聚合，写入按日书籍/章节阅读统计表，处理幂等、批量更新和消费积压。
3. **再下一阶段：推荐接入。** 将点击量、有效阅读时长等特征接入推荐排序，先离线或定时计算，再做效果验证。
4. **上线准备。** HTTPS、Nginx、密钥注入、网络隔离、限流压测、监控告警和数据合规检查。

## 12. 方案取舍

已选择“Redis 闸门后直接生产 Kafka”，而不是仅写 Redis 或当前阶段直接落 MySQL，原因是：

- Redis 适合低延迟原子校验，但不适合长期保存统计事实。
- Kafka 隔离高频心跳和后续数据库聚合，能削峰并允许消费端批处理。
- 请求线程不访问 MySQL，避免阅读心跳反过来拖慢核心阅读链路。
- 事件不携带匿名身份数据，兼顾后续聚合价值和隐私最小化。

代价是 Kafka 失败时允许少记少量时长，并且当前阶段只生产、不落库。该数据用于热度和推荐而非计费、结算或权益判断，因此选择可用性优先和最终近似统计是合理的；如果未来用于强一致业务，需要重新设计可靠投递与幂等存储。
