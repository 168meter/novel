# 章节阅读高并发基线与缓存设计

## 目标

为 `novel-front` 建立可重复的性能工程闭环：使用 JMeter 测量当前章节阅读链路的容量拐点，定位瓶颈，增加章节正文缓存与热点保护，再以相同环境和负载复测，用数据证明改造效果。

本阶段不引入 Kafka、Elasticsearch、微服务或云部署，避免多个变量同时变化导致测试结论失真。

## 当前链路

章节页面 `GET /book/{bookId}/{bookIndexId}.html` 由 `PageController` 处理。数据库存储类型的正文通过 `DbBookContentServiceImpl.queryBookContent` 直接查询 MySQL 分表，当前没有章节正文 Redis 缓存。页面触发的 `POST /book/addVisitCount` 直接更新 MySQL 热点行，应作为独立写场景测量，不与第一轮正文读取基线混合。

项目已有 Redis 能力，并用于首页数据、榜单、新闻、友情链接和评论点赞。本阶段复用现有 `CacheService`/Redis 配置，但为章节缓存定义独立键空间、过期和失效规则。

## 测试模型

### 第一轮：单接口容量基线

选择数据库中真实存在的一本书和一个免费章节，固定测试章节页面。JMeter 依次运行 1、10、30、50、100、200 个线程，每档预热后持续 60 秒。正式测试使用非 GUI 模式，禁用 `View Results Tree`，保存 JTL 并生成 HTML 报告。

每档记录：

- 实际吞吐量（requests/second）
- P50、P95、P99 响应时间
- HTTP 错误率和超时数
- Java 进程 CPU、堆、GC、线程数
- Hikari 活跃连接和等待连接
- MySQL 查询量、连接数、慢查询和锁等待
- Redis 命令量、延迟、命中与未命中

容量拐点定义为：继续增加线程时吞吐量增幅明显变小，同时 P99 或错误率快速上升。单机环境不设虚假的固定 QPS 门槛，以同机、同数据、同脚本下的前后变化作为核心证据。

### 第二轮：缓存命中复测

加入章节缓存后，使用完全相同的章节、线程阶梯和持续时间复测。报告必须分别标记冷缓存首访和缓存预热后的稳定状态，避免用预热结果冒充首次访问性能。

### 第三轮：故障与正确性测试

同时请求一个刚过期的热门章节，验证只有受控数量的请求回源 MySQL；重复请求不存在的章节，验证空值缓存或等效保护有效；作者修改章节后，验证旧缓存被删除且下一次读取获得新正文；Redis 不可用时，验证请求受控回源或快速失败，不造成无限等待。

## 缓存设计

采用 Cache-Aside：

1. 根据 `bookId` 与 `bookIndexId` 读取 Redis。
2. 命中则反序列化并返回。
3. 未命中时使用短时互斥锁保护热点键。
4. 获得锁的请求再次检查缓存，再查询 MySQL 并写入 Redis。
5. 未获得锁的请求短暂退避后重试缓存，超过限制后受控回源或失败，不无限自旋。

缓存键包含版本前缀，例如 `novel:chapter:v1:{bookId}:{bookIndexId}`。正常正文采用带随机抖动的过期时间，避免大量章节同时失效；不存在的章节使用短期空值缓存，避免穿透。作者新增、修改或删除章节时删除对应缓存，下一次读取重新加载。

锁必须设置唯一值和有限租期，并通过校验唯一值的 Lua 脚本释放，避免误删其他请求持有的锁。缓存异常不得改变数据库中的正文数据。

## 访问量写入边界

`addVisitCount` 不计入章节正文缓存的第一份性能结论。它单独建立写压测基线，后续演进为 Redis 计数聚合与 Kafka 异步落库。分离读取和计数测试，可以明确章节缓存解决了什么，也避免把异步计数收益错误归因于正文缓存。

## 产物

- `performance/jmeter/chapter-baseline.jmx`：参数化章节基准计划
- `performance/README.md`：运行方法、环境记录和指标解释
- `performance/results/`：忽略大型原始 JTL，只保留小型汇总或报告模板
- 章节缓存实现及单元/集成测试
- 优化前后对比报告，记录硬件、JVM、Docker、数据、负载和结果

## 验收标准

所有结论必须来自相同测试环境和负载：

- 缓存预热后，章节相关 MySQL 查询量相较基线下降至少 90%
- 稳定区间内 P99 相较基线下降至少 60%
- 稳定吞吐量至少达到基线的 3 倍，若负载机或本机资源先饱和，报告必须明确限制来源
- HTTP 错误率低于 0.1%
- 热点缓存同时失效时，不出现与并发数等量的 MySQL 回源
- 不存在章节不会持续穿透数据库
- 章节修改后读取不到旧正文
- Redis 故障测试不会导致请求无限等待或线程池持续堆积

## 非目标

- 本阶段不声称达到生产级固定 QPS
- 不使用 JMeter GUI 结果树作为正式性能数据
- 不在同一份测试中同时修改缓存、线程池、SQL和 JVM 参数
- 不缓存 VIP 权限判断结果来绕过现有购买与鉴权流程
- 不实现 Kafka 点击聚合、搜索、推荐或微服务拆分
